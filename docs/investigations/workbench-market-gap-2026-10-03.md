# 漫剧 Workbench 竞品与产品差距调研

调研日期：2026-10-03。代码基线：`a374963`。目标：零门槛、上手快、产量大。

本轮只调研和验证，不修改产品代码。以下先按个人创作者 / 小团队制作竖屏连载漫剧评估；电影级短片需要不同的质量、时间与成本取舍。

## 结论

当前产品已经具备可干预的制作链路、Provider / Capability、资产版本、局部重做、质量审核、项目提示词、免费教程和按集制作配置。它更适合愿意学习制作流程、自己配置模型的创作者。

距离用户提出的三个目标，优先缺口是：

1. 普通用户无需理解模型和制作术语的首次创作入口。
2. 能完整交付声音、字幕和成片的标准制作流程。
3. 真正能连续运行、多集复用、遇错可恢复的批量生产队列。

现有教程能帮助理解流程，但没有消除真实创作中的配置、选择和操作成本。现有批量生成与 `auto_continue` 也不等于已经具备稳定的连续量产能力。

### 1. 「零门槛」首先是服务接入问题

README 的真实首次流程是：添加 Provider → 填 Key → 拉取 / 启用模型 → 设默认模型。即使每一步有说明，普通用户仍需先学会 API。

两个合理方案：

- **继续 BYOK**：先做推荐服务的一次配置向导，用户只填 Key，系统在明确配置范围内完成模型用途、验证和默认值设置。改动较小，保留本地数据与用户自付模型费用，但只能降低门槛。
- **平台代管服务**：用户登录 / 购买额度后即可制作，BYOK 留在高级设置。若「零门槛」是硬目标，更符合目标；代价是引入服务端凭据、账户计费、额度预留、运营和售后。

推荐分开决策：近期先简化 BYOK 接入，验证第一集体验；面向大众的版本再由项目负责人确认平台代管的商业与技术范围。不能靠前端隐藏表单实现零配置，也不能将统一服务凭据放进客户端。

### 2. 新手需要制作向导与完整生产预设

推荐简单模式的默认路径：

故事 / 剧本输入 → 选择风格与目标时长 → 审核人物和整集故事板 → 查看本次制作范围 / 额度 → 制作 → 只处理异常镜头 → 导出。

专业模式保留现有逐环节编辑。简单模式自动建立 Bible、剧本结构、资产引用和阶段配置，将用户判断集中在人物与故事板等少数关键节点。付费制作的授权应覆盖明确集数、镜头数和重试额度；发生计划之外的增加时再请求确认。

预设不是提示词合集，应同时描述画风、节奏、景别倾向、目标比例、参考图要求、声音配置、字幕和交付规格。模型按配置与 Capability 解析，并在生成前展示实际选用结果。

小说和现成剧本应提供不同起点：已有剧本可直接进入场景 / 资产准备，不强迫先创建一部小说。已审核的全局角色资产应能供后续集数复用，不重复生成。

### 3. 「产量大」要有不同制作成本的模式

建议先集中做好旁白 / 对话驱动的短篇连载，而不是要求所有镜头都达到电影级全动态效果。

- 动态漫画快速模式：可复用插画 + 本地推拉 / 平移 + 配音 + 字幕，用少量生成视频承载关键动作。
- 标准漫剧模式：对话和静态镜头复用资产，动作 / 转场镜头使用图生视频。
- 高质量模式：逐镜头视频生成和精修，明确更高制作成本和等待。

这是拟议产品能力，当前尚未实现。它能减少需要生成的视频镜头数量，但产量和成本改善要用真实项目测量，不能预先给倍数承诺。简单模式只暴露经测试的稳定方案。

### 4. 有声成片交付存在明确断点

代码依据：

- `apps/backend/app/services/pipeline_service.py:37` 的按集阶段为分镜、图片和视频，视频请求在 `:561` 明确 `with_audio=False`。
- `apps/desktop/src/pages/StoryboardPage.tsx:2692` 已有单镜头「生成声音」，资产页 `AssetPage.tsx:821` 已有角色 `voice_id`。因此不是「完全没有配音」。
- `audio_dubbing_service.py:370` 将配音结果保存为 `shot_video_voiced`；`video_sequence_service.py:74` 的场景合成却取 `shot_video`。当前合成路径没有优先纳入独立配音结果。此项来自静态调用链核对，本轮未运行真实音频合成验证。
- 未发现产品级自动字幕生成 / 编辑 / 成片烧录流程；教程短片中的字幕属于预置媒体，不代表真实产品支持。

建议优先闭合：全剧角色声音设定 → 整集配音 / 原生音频选择 → 对白时序与字幕 → BGM 音量处理 → 有声版本合成 → 整集预览 → 标准 MP4 与字幕交付。首版只需基础排序、裁切和声音 / 字幕控制，无需重建完整专业剪辑软件。

### 5. 批量生产前先修复调度正确性

`job_worker.py:124` 单 Worker 顺序领取任务；`:272` 同步执行流水线。按集流水线创建生成子任务后，`pipeline_service.py:471` 轮询等待其完成；子任务又需要同一个 Worker 领取执行。

**隔离复现结果**：使用 `tests/test_episode_pipeline_service.py` 的临时项目与真实 JobStore / Pipeline / Worker，将测试夹具原本「创建后立即完成」的生成模拟改为仅创建 queued Job。父任务开始后，跨过一个轮询周期仍为 `running`，子任务为 `queued`，Worker 阻塞。取消父任务后 Worker 释放。

```json
{
  "reproduced": true,
  "parent_status": "running",
  "child_status": "queued",
  "worker_blocked_waiting_for_child": true,
  "cancel_released_worker": true,
  "provider_requests": 0,
  "user_data_accessed": false
}
```

这是当前调度组合的复现，不是 Provider 速度测试。已有 Pipeline 单测使用立即完成的子任务，不能覆盖这条真实排队路径。首次验证在 Windows 临时 SQLite 清理时遇到文件锁，已清理；随后释放连接再复验，复现与临时数据清理均成功。

建议先使编排器不占住唯一执行 Worker：子任务完成驱动下一步，或者为编排与生成分离受控执行资源。验证暂停、取消、崩溃恢复和重复领取，再考虑并发。不要以无限增加线程解决。

可控并发指多个独立镜头 Job 同时执行，每个 Job 仍只绑定一个 Model / Provider。它不要求多模型同时为同一镜头抽卡；但当前路线的「不并行」约束需由项目负责人明确是否允许放宽到独立任务并发。

需要的批量产品行为：选择集数范围、总镜头数 / 时长 / 额度预检、项目 / Provider 并发上限、持久化远程 task_id、轮询恢复、失败项集中处理、仅重做选定异常项、跳过已有可用结果、连续出片与统一命名。平台不支持精确取消时，应准确展示取消范围。

### 6. 用实际产出数据指导优化

`model_router.py:6,60` 当前速度 / 经济偏好部分来自名称中的 fast、mini 等标识，不能据此认定真实速度或费用。

建议记录：请求次数、输入 / 输出用量、Provider 可返回的费用、排队 / 生成耗时、失败类别、人工采用 / 重做结果。价格缺失时显示未提供；有可靠计价时再给预估范围。预算系统应在提交前预留预计额度，结算后释放差额，不只在发出请求后计数。

审核 AI 可以帮助筛选异常，但不能保证生成正确，更不能默认无限重试。把自动补救限定在用户已授权的批次 / 次数 / 额度内，避免返工成本失控。

## 推荐实施顺序

| 阶段 | 最小可交付成果 | 验收重点 |
| --- | --- | --- |
| S0：生产可靠性 | 修复父子任务调度、明确合成的有声版本选择，补真实排队生命周期验证 | 一个批次不会等待无法执行的子任务；暂停 / 取消 / 重启后状态正确；配音结果能进入成片 |
| S1：第一集向导 | 简单模式 + 推荐接入向导 + 少量经过验证的制作预设；专业模式继续可用 | 新用户无需学习 Bible / Capability / Prompt 也能审核故事板并开始制作 |
| S2：可发布成片 | 角色声音、整集音频、字幕、基础节奏、成片规格与交付包 | 从导入内容到有声带字幕 MP4 在应用内完成；可预览、局部修正 |
| S3：连续生产 | 已调通预设复用、多集队列、额度控制、异常批量处理、按 Provider 限额的独立任务并发 | 三集试生产连续完成，成功结果不重复提交；失败项可单独处理 |
| S4：扩大规模 | 跨项目制作方案、产能 / 成本统计；有明确团队需求后再做共享审片 | 复用节省人工操作，返工和实际费用可追踪 |

「零门槛」和「高产量」应基于 S0–S3，而不是先增加自由节点画布、3D 导演台、更多模型数量或更多提示词字段。结构化导演控制可以保留为专业增强，优先服务降低返工的明确问题。

## 如何衡量三个目标

以下是建议验收目标，不是目前测得的结果：

- 首次使用：找 5 位没做过漫剧的用户，是否至少 4 位能在不接受口头帮助的情况下完成故事板审核并进入制作；记录失败位置。
- 上手速度：将用户主动配置 / 操作时间与模型等待时间分开。第一集主动操作时间先以 10 分钟以内为验证目标。
- 完成交付：以 60–90 秒、有清晰声音与同步字幕的竖屏 MP4 作为小规模样本；不只统计生成了多少片段。
- 连续产量：同一人物 / 风格 / 制作方案连续 3 集，检查需要多少重复配置与人工干预，以及能否只处理异常项。
- 单位成本：每个最终采用的视频分钟的实际模型费用；未知费用不假装精确。
- 返工：镜头首次人工采用率、每个采用镜头的平均生成次数和人工修正时间。
- 可靠性：取消、网络中断、Provider 429 / 5xx、重启恢复、重复点击，都不会重复扣费提交或丢失可用结果。

单人每天可发布的有效分钟，取决于人工处理能力、模型吞吐和费用额度中最紧的一项；还要扣除返工。不能用 API 请求数或原始视频秒数代替产量。

若要进一步做产量 / 成本实测，需要先约定作品时长、镜头复杂度、质量标准、服务商和测试费用；本轮没有执行此类付费验证。

## 当前需要产品负责人决定的边界

1. 面向大众的版本是否引入账户 / 统一额度代管，还是坚持 BYOK。
2. 是否优先推出动态漫画 / 混合模式，接受部分镜头使用插画运镜以换取产量。
3. 是否允许不同镜头 Job 在 Provider 限额和预算内并发，保留单 Job 单模型约束。

最合理的下一步是先做 S0：修复已复现的调度阻塞并验证有声合成，再实现简单模式与成片交付。尚未修改现有路线图，也未执行任何产品实现。
